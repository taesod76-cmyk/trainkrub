# Database scripts

Run these in the Supabase dashboard → SQL Editor.

## First install (in this order)

1. `01_install.sql` — adds the private tables and the server functions. Safe to run more than once.
   The website keeps working while it runs. Existing passwords are converted to bcrypt hashes.
2. Create the admin sign-in (choose your own name and a long password; do not keep it in any file):

   ```sql
   select app_private.admin_set('your-admin-name', 'a-long-password-of-12-or-more-characters');
   ```

   Running it again later replaces the admin password, signs the admin out everywhere and clears any
   lockout (use it if the admin is ever locked out).
3. Publish the new website version (this repo → GitHub Pages).
4. `02_lockdown.sql` — only after step 3. Removes the old open policies so nobody can read or write the
   table directly any more; only the server functions can.

After step 4 nobody (including someone holding the public key) can read the data table, list users, or
read a password, and every sign-in attempt, wrong password and sensitive action is logged in
`app_private.audit` (kept 180 days; readable only from the SQL editor).

`01_install.sql` always contains everything in the update scripts below, so a brand-new install needs
only the four steps above.

## Updating a database that is already installed

Run the updates you have not run yet, in this order. Each is safe to run more than once and only replaces
server functions (`05` also closes out requests that were still waiting, see below).
Run it **before** publishing the website version that goes with it.

- `03_update_trainer_signup.sql` — trainers who apply are accepted at once (no waiting for the admin).
- `04_update_light_refresh.sql` — lighter background refresh: a small call for the admin dashboard numbers,
  no profile pictures in the admin's lists, and suspending a user keeps the stored picture.
- `05_update_auto_confirm.sql` — a customer's booking is confirmed at once and goes straight onto the trainer's
  schedule (the trainer already set the notice time). Requests that were still waiting today are turned into
  bookings: when two people asked for the same time the first one gets it and the other is declined, and times
  that have already passed are closed. After it ran, no booking stays "pending".

- `06_update_push.sql` — pop-up notifications on phones (see the section below). It only adds new things; nothing the
  website uses today changes. It is safe to run before or after the `push-send` function is added.

- `07_update_trainer_rules.sql` — a booking needs a package of **that** trainer, and health information (see the section
  below). It only replaces server functions; no stored data is changed. Run it **before** publishing the website version
  of round 17. The last lines show a check list: the first line must say `ok`; the second tells how many active packages
  name no trainer (old packages from the former admin catalogue). Those can no longer be used for booking.

## Pop-up notifications on phones

Every new in-app notification can also pop up on the person's phone (like Facebook or LINE), even when the app is
closed. Each person turns it on per device in the app (Notifications page, or the banner on the home page).

How it works: the website asks the phone's browser for permission and stores a "subscription" (one per device) through
`app_push_subscribe`. When a new `notif:` row is saved, a database trigger calls the `push-send` Edge Function
(through the `pg_net` extension). The function reads the notification and that person's devices through
`app_push_take`, encrypts the message (RFC 8291) and sends it with VAPID keys to the phone makers' push servers
(Google, Apple, Mozilla, Microsoft). A notification is always saved, even if the pop-up cannot be sent.

One-time setup (in the Supabase dashboard):

1. SQL Editor → run `06_update_push.sql`. The last lines show a check list. If `pg_net` says OFF, turn it on at
   Database → Extensions and run the script again.
2. Edge Functions → Deploy a new function → Via Editor → name it exactly `push-send` → paste
   `supabase/functions/push-send/index.ts` → turn **Verify JWT off** for this function (the database calls it with
   its own secret, not with a user token) → Deploy.
3. Open the website, go to Notifications → "Turn on for this device".

Nothing secret is written in any file: the secret that the database and the function share is generated inside
the database by `06_update_push.sql`, and the VAPID key pair is generated by the function the first time it runs and
stored in `app_private.push_config` (not readable through the API).

Look at what happened (SQL Editor): `select * from app_private.push_log order by id desc limit 20;`
(one line per sent notification: how many devices got it, how many were removed because the phone had
uninstalled / revoked, how many failed, and the answer codes). Requests the database made to the function:
`select id, status_code, left(content::text, 120) from net._http_response order by id desc limit 10;`
(401 here means the function still has Verify JWT on).

## Trainer sign-up

A trainer applies with a password or with Google. The server creates the trainer account, the trainer
code and the sign-in token in one step, and the app opens the trainer dashboard straight away.
Certificate pictures are uploaded one by one before that step with a single-use upload token. If the
upload step is cut off, the application is completed the next time the applicant signs in with the same
password or the same Google account. The admin can still suspend any trainer from the admin page.

## Packages belong to their trainer

A package bought from a trainer only works with that trainer. The server refuses a booking whose package belongs to
another trainer, or names no trainer at all (the old packages from the former admin catalogue), and refuses a day after
the package's expiry date. The website shows the same rule: the booking page says which trainer the customer's packages
work with and offers the "buy a package" button.

## Health information

A customer can fill in health information on the profile page: long-term conditions, injuries, medicines / allergies,
goal, age, weight, height and an emergency contact. Filling anything in needs the customer's tick on the agreement
(the server answers `consent_needed` without it). It is stored in the customer's row (`health`).

- the customer reads and edits their own;
- a trainer reads it only when the customer agreed **and** they really work together: the customer has a package with
  that trainer (active, used up or expired) or a booking that stands (waiting, confirmed, done or no-show). When the
  package is cancelled and no booking stands, the trainer sees the basic profile but not the health information;
- the admin never sees it (it is left out of every admin read and list; suspending a customer keeps it untouched);
- nobody else can read or write it.

Read access is decided in `app_private.read_view` and `app_private.trainer_sees_health`; writing is validated in
`app_private.w_customer` (text limits, number ranges, phone format).

## Booking up to 14 days ahead

The booking page lets a customer pick several days and times and book them all at once (the website books them one by
one; each is checked by the server as before: the package of that trainer, sessions left minus open bookings, the
trainer's notice time, first come first served, at most 30 open bookings per customer).
